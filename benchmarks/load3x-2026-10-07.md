# 3× steady state — TASK-021 step 8 (slice 11.2i)

**Lab, not production.** Same posture as [`baseline-2026-10-02.md`](baseline-2026-10-02.md):
seed 1 scale data (`sanvi_scale`), compose Postgres 18 on port 5433, release
build 0.10.0 (rebuilt from current main before the run — 11.2b–h included),
Redis caches warm, rate limiting disabled, tracking abuse quota raised.
Machine profile `{"cores":20,"mem_gb":16,"os":"Windows 11 26200","arch":"x86_64"}`,
host shared with unrelated Docker stacks (recorded; see the noise note).

- **Date:** 2026-10-07
- **Shape:** all five k6 shapes **concurrently**, each at 3× its offered
  rate, for 300 s — the harness's projected peak is the five-shape mix
  (230 iterations/s offered), so 3× is 690 iterations/s offered, 690×
  per-shape rates of 150 / 60 / 30 / 300 / 150. Artifacts:
  `benchmarks/<scenario>/x3.json` (tag `x3`, stats_version 2).
- **Sampler:** `benchmarks/load3x-2026-10-07/samples.txt` — 2 s nominal
  cadence (~5 s effective under load: typeperf + PowerShell + docker exec
  per sample), 70 samples. Columns: host CPU, per-process RSS / threads /
  handles / CPU, api pool gauges, pg_stat_activity by `application_name`.
  A first capture (09:12–09:17, kept as `samples-no-cpu.txt`) preceded a
  sampler fix that added the CPU columns; its `x3.json` artifacts were
  overwritten by the recorded run, its numbers were materially identical
  (storefront p95 11.0 ms vs 9.3 ms).

## Result: every budget holds, every resource under 70 % — most under 10 %

252,007 HTTP requests completed over 300 s (840 req/s; 690 iterations/s
offered — storefront and webhook iterations issue two requests each),
**0 failed, 0 dropped** on every shape.

| shape | offered | p50 ms | p95 ms | p99 ms | budget | verdict |
|---|---:|---:|---:|---:|---|---|
| storefront_read | 150 | 4.53 | **9.31** | 22.0 | ≤ 200 ms | 4.7 % of budget |
| admin_write | 60 | 4.21 | **9.78** | 23.2 | ≤ 400 ms | 2.4 % of budget |
| checkout_create | 30 | 4.23 | **10.22** | 25.3 | ≥ 99.5 % success | 100 % (lab 401 boundary) |
| webhook_flood | 300 | 2.09 | 5.52 | 15.3 | p99 < 30 s to effect | front door only (standing gap) |
| conversion_upload | 150 | 2.88 | 7.44 | 18.9 | ≥ 99 % per sweep | 100 % capture (sweep is worker-side) |

The 94 % host-CPU sample is host-wide, not the API: five k6 generator
processes, the WSL2 Docker VM, and several unrelated co-tenant stacks
(ragflow/Elasticsearch, a kind control plane) share the machine. The API
itself never exceeded 13.1 %. On a dedicated host the headroom is larger;
the co-tenancy is recorded because it is the honest description of every
number on this page.
