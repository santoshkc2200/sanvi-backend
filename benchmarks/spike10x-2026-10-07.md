# 10× spike — TASK-021 step 8 (slice 11.2i)

**Lab, not production.** Same posture as
[`load3x-2026-10-07.md`](load3x-2026-10-07.md). Two spike runs, identical
parameters, materially different degradation shapes — that instability is
itself the finding, and is why both are recorded.

- **Date:** 2026-10-07
- **Shape:** all five k6 shapes **concurrently** at 10× their offered rates
  (500 / 200 / 100 / 1000 / 500 iterations/s — 2,300 iterations/s offered
  aggregate), for **120 s**. Artifacts: `benchmarks/<scenario>/x10.json`
  (tag `x10`). Recovery artifacts: `benchmarks/storefront_read/rec.1.json`
  and `rec.2.json` (offered-rate storefront runs immediately after each
  spike) plus the API process start time, unchanged across both.
- **Client-side ceiling, stated first:** the harness's constant-arrival
  executor caps VUs at `rate × 4` (`tests/load/lib.js`), so k6 warns
  "Insufficient VUs … cannot initialize more" on every shape here — once
  server latency exceeds ~4 s, the client cannot hold the offered rate and
  records the shortfall as dropped iterations. **The server never received
  the full 2,300 iterations/s.** Raising the cap is a harness change, not a
  server property; recorded rather than patched, because the drops are part
  of what this run measures.

## Reading both runs together

- **Near the knee, whichever resource saturates first wins.** Run A: host
  CPU high (76 %), pool idle 8–10 — CPU-shaped contention. Run B: host CPU
  mid (37–46 %), pool idle 1 with ~1 s acquire waits and RSS ballooning —
  pool-shaped queueing. Same offered load, same build, minutes apart, on a
  host shared with co-tenant stacks. **The lab cannot localise a single
  10× ceiling**, and this record does not pretend to: what it establishes
  is that the system is healthy and well clear of the knee at 3×
  ([load3x](load3x-2026-10-07.md)), and degrades — rather than crashes —
  somewhere between 3× and 10×, through either the CPU or the 10-connection
  pool depending on which the host yields first.
- **No restart, no 5xx storm.** Both runs: the API process survived with
  its start time unchanged, error rates stayed under 0.5 %, and the pool
  failures counter moved by 3 across run B (of 10 connections, saturated
  for ~2 min under a 2,300 iterations/s offer).
- **Recovery is immediate and complete.** Immediately after each spike,
  the offered-rate storefront shape ran clean: rec.1 p95 6.53 ms, rec.2
  p95 6.73 ms, both 0 failed / 0 dropped, `healthz` 200. RSS does not
  return to its pre-spike ~100 MB — it plateaus at ~460 MB (Windows heap
  retention after the burst). The 24 h soak
  ([soak-2026-10-07](soak-2026-10-07/README.md)) watches exactly that
  plateau for 24 h: flat is the pass condition.

## What TASK-023 takes from this

The measured input for shedding thresholds: healthy ceiling ≥ 3× the
projected peak; degradation onset between 3× and 10×, via pool saturation
(1 s acquire waits) or CPU — with the pool's acquire-wait alert
(`DbPoolAcquireWaitHigh`, fires at 100 ms p95) sitting well below the
observed 1 s waits, i.e. the alert fires before the collapse this record
shows, on both bottleneck shapes. The shared-host caveat transfers with it:
a dedicated host will localise the knee differently.
