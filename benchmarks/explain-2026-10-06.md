# Query plan review — keyset reads, slug lookup, RLS predicate cost (TASK-021 11.2d)

**Lab, not production.** Produced on the 11.2 capture host (Windows, 20 cores /
16 GB), against a locally composed Postgres 18 seeded by the plan gate's own
seed (`apps/api/tests/perf/explain_assertions.rs`): three page-sized tenants on
the read models plus 3,000 background tenants for the platform surfaces —
2,000 invoices / payments / checkouts / audit entries per tenant, 1,000 DSRs,
900 domains, 600 orders / disputes / users / memberships, 500 invitations /
campaigns, 1,500 live hostnames, then `ANALYZE`. This is the input step 3
judged from; every index decision below was measured on it, not inferred.

## What was wrong (before-plans, application role, tenant GUC set)

The 11.2b cursor pagination made `WHERE tenant_id = $1 … ORDER BY id DESC
LIMIT $n` the read shape of every collection endpoint, but the supporting
indexes predate it. The planner walked each table's **primary key** backward —
which orders by `id` and therefore serves the keyset for free — and filtered
by tenant as it went, so a page cost reading every newer row **on the
platform**:

| Read (profiled endpoint) | Before plan (seed: 3 tenants × 2,000 rows) | Waste |
|---|---|---|
| invoices first page (`tenant_invoices`) | Index Scan Backward on `invoices_pkey`, tenant as Filter | **4,000 of 6,000 rows removed by filter** per 200-row page |
| invoices page 2 | same, cursor as Index Cond | reads all newer non-tenant rows back to the cursor |
| DSR tenant keyset (`tenant_privacy-requests`) | `data_subject_requests_pkey` + Filter | 2,000 removed per 100-row page |
| invitations keyset | `invitations_pkey` + Filter | 1,000 removed per 50-row page |
| audit seq keyset | `audit_entries_seq_unique` + Filter | **2,999 removed per 50-row page** (grows with platform size) |
| custom_domains / orders keysets (`tenant_domains`) | pkey + Filter | walk-back between cursor and matches |
| disputes keyset | `disputes_tenant_idx (tenant_id)` then sort | sort per page (no cursor match) |
| slug availability (`public_slug-availability`) | **Seq Scan on tenants** — `WHERE slug = $1` cannot use the `lower(slug)` expression index | full scan per availability check |

Already served (guarded, not changed): payments page
(`payments_tenant_created_id_idx`, from 20260824050000), campaigns keyset
(`UNIQUE (tenant_id, id)`), members keyset (`memberships_pkey`), the
live-hostname resolution (`live_hostnames_pkey`, the baseline's dominant
statement at 0.022–0.026 ms mean), plan entitlements/prices fanout reads
(PK/partial-index eligible — see "reviewed and left" below).

## The fixes (`migrations/20261006000000_perf_keyset_indexes.sql`, after-plans)

| Index | Action | Query it serves |
|---|---|---|
| `billing.invoices (tenant_id, id DESC)` | realigned from `(tenant_id, created_at DESC)` — no query orders invoices by `created_at` since 11.2b | invoices keyset (both pages) |
| `privacy.data_subject_requests (tenant_id, id)` | added — no tenant index existed | DSR tenant keyset |
| `identity.invitations (tenant_id, id)` | added — no tenant index existed | invitations keyset |
| `audit.entries (tenant_id, seq)` | added — `(tenant_id, occurred_at)` cannot serve seq order | audit tenant seq keyset |
| `domains.custom_domains (tenant_id, id)` | realigned from `(tenant_id)` | custom-domains keyset |
| `domains.orders (tenant_id, id)` | realigned from `(tenant_id)` | orders keyset |
| `payments.disputes (tenant_id, created_at DESC, id DESC)` | realigned from `(tenant_id)` — same shape payments got in 20260824050000 | disputes keyset |
| `tenancy.tenants (slug)` | replaced `lower(slug)` expression — the CHECK `slug = lower(slug)` makes them equivalent | slug availability, find_by_slug |
| `tenancy.tenants (created_at DESC, id DESC)` | added | platform tenant browse keyset |

After: every keyset page is `Index [Only] Scan (Backward) using <the tenant
index>`, Index Cond carrying `(tenant_id = $1 AND id < $cursor)`, **zero rows
removed by filter**; slug availability is an index-only unique scan at scale.
The plans are pinned by `apps/api/tests/perf/explain_assertions.rs` (14 rules;
drop the index and the failure names the flip — see the drill below).

The RLS predicate appears in every plan as a Filter above the index cond and
costs nothing the index did not already pay: on the pinned plans it removes
zero rows (the index delivered the tenant's rows).

## RLS predicate cost per table

Method: `SELECT count(*)` over the whole (seeded) table as `sanvi_app` with
`set_config('sanvi.tenant_id', …)` — predicate evaluated per row — versus the
same statement as superuser (RLS bypassed). EXPLAIN ANALYZE, best of runs;
lab numbers on the seeded volumes above.

| Table | rows | app + RLS | superuser | predicate adds |
|---|---:|---:|---:|---:|
| `audit.entries` | 6,000 | 1.068 ms | 0.500 ms | ~0.095 µs/row |
| `billing.invoices` | 6,000 | 1.044 ms | 0.453 ms | ~0.099 µs/row |
| `payments.payments` | 6,000 | 1.069 ms | 0.532 ms | ~0.090 µs/row |
| `privacy.data_subject_requests` | 3,000 | 0.619 ms | 0.337 ms | ~0.094 µs/row |
| `advertising.campaigns` | 1,500 | 0.352 ms | 0.157 ms | ~0.130 µs/row |
| `domains.custom_domains` | 2,700 | 0.490 ms | 0.211 ms | ~0.104 µs/row |

Scoping correctness was asserted alongside (each tenant sees exactly its own
rows through the policy). Reading: the canonical RLS predicate costs on the
order of **0.1 µs per row evaluated** on this host — real but noise next to
any page fetch. It is a per-row Filter **after** index delivery: when the
query leads with `tenant_id` (every pinned plan does), the predicate removes
zero rows and adds nothing measurable to the endpoint shape. `count(*)`-style
whole-table reads are the only shape where the predicate is exposed, and no
endpoint runs that shape.

## The plan-stability trap this slice had to design around

With the indexes in place, the keyset plans still flipped between two shapes
depending on the **visibility map**:

- **Map filled** (autovacuum has passed): the composite index is served
  `Index Only Scan`, Heap Fetches 0 — wins outright.
- **Map empty** (fresh bulk load): Postgres declines to mark freshly-committed
  pages all-visible for a short aging window, and without the map the planner
  prefers the pkey walk for cursor pages — the composite's heap-fetching plan
  ties the pkey's and loses the tie. Measured repeatedly: same statements,
  flip on VACUUM/autovacuum alone; the OR-shaped `($2 IS NULL OR id < $2)`
  cursor is **not** the variable (it flips identically with a plain cursor
  bind).

Production reaches the filled map within autovacuum's first pass after any
bulk load; the transient window is TASK-028's vacuum-tuning territory. The
gate pins the **steady-state** plans: its fixture is a shared database built
once per (migration set, seed) pair — cloned from the migrated template,
seeded, then polled until the map fills (autovacuum's pass; manual VACUUM
marked nothing here even minutes later) — and used read-only from then on.
The probe is the invoices keyset query itself, served `Index Only Scan …
Heap Fetches 0` exactly when the map is filled.

## Falsifiability drill (the slice's verify line)

`billing.invoices_tenant_idx` dropped in a scratch clone of the fixture, the
page-2 rule re-run in place:

```
Limit → Index Scan Backward using invoices_pkey on invoices
        Index Cond: (id < '911031001000')
        Filter: ((tenant_id = 911000001) AND (RLS predicate))
```

Not a Seq Scan — the flip is invisible to a "no Seq Scan" check, which is why
each rule pins the index name. The checker's failure message names both sides
(`expected the plan to use index 'invoices_tenant_idx' on billing.invoices;
found: Index Scan Backward using 'invoices_pkey' …`), proven by the fixture
test `a_dropped_index_fails_naming_the_flip` on exactly this plan shape.

## Reviewed and left

- `localization.translations` — reads lead with `scope`; the PK
  `(scope, key, locale)` prefix serves them, and the measured hot statement
  (the whole platform catalog per request) is a scan **by design**.
- `billing.plan_entitlements` / `plan_prices` — the planner seq-scans at lab
  distribution (86 % of rows match `plan_id`) and would be right to; the
  public_plans cost is the per-plan fanout (1,803 calls per 601 requests),
  step 4's first target, not an access-path problem.
- `payments.checkouts` — no read model orders checkouts by id within a
  tenant; the `(tenant_id)` index stays. `find_by_reference` sorts per call;
  a `(tenant_id, reference)` index is a candidate if callbacks get hot —
  needs a uniqueness assumption verified first.
- `tenancy.tenants` search term is infix `ILIKE` — no btree serves it; a
  pg_trgm GIN index is the production answer if platform tenant search grows
  past the bounded page, deliberately not added here (extension dependency
  + write cost on a platform-admin surface).
- `checkouts.customer_ref::text ILIKE` cannot use the existing GIN index
  (jsonb_ops serves `@>`, not ILIKE) — already documented at its definition
  site (20260824050000); the filter is tenant-bounded.
- `access.roles`, `supported_locales`, `reserved_slugs` — catalogs of rows a
  client cannot influence; seq scans are optimal at any realistic size.
