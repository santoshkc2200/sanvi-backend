# Query and cache baseline — seed 1 scale data (TASK-019 step 6)

**Lab, not production.** Every number below was produced on the machine
profile recorded here, against a locally composed Postgres 18 in Docker on a
developer laptop, with the API in the debug build (the release profile
currently fails to link on this host — sqlx-macros dylib; see execution
notes in the TASK-019 task file). It is the input TASK-021 profiles against
and TASK-028 measures bloat from. Nothing here is a capacity claim.

- **Seed:** 1 · **checksum:** `1d6a6ef47d50527cff4fae065d7d4d30b229f93512597170bb6d8198f79214f7` · **total rows:** 48,608
- **Build stamp:** `{"built_at":"unknown","commit":"unknown","environment":"local","version":"0.10.0"}` (local build: commit/built_at unset — the
  pipeline stamps release binaries; the *endpoint* is what this task ships)
- **Machine profile:** `{"cores":10,"mem_gb":16,"os":"Darwin 27.0.0","arch":"arm64"}`
- **Load:** five k6 shapes, 60 s each at the offered rates
  (storefront_read 50 rps, admin_write 20, checkout_create 10,
  webhook_flood 100, conversion_upload 50) against
  `SANVI__DATABASE__NAME=sanvi_scale`, per-IP and per-tenant rate
  limiting disabled, `features.advertising` on with dev-only signing
  secrets so the beacon route is wired.
- **Warm-cache posture:** Redis (resolution + resolved-theme caches) was
  warm from prior runs; the statement table below is therefore the
  *steady-state* query mix, not a cold-start one.
- **pg_stat_statements** was enabled for this capture
  (`shared_preload_libraries` + `CREATE EXTENSION`) — the compose
  default ships without it; TASK-021 will want that permanent.
