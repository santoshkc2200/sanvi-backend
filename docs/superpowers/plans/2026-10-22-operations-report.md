# Deployment and proxy remediation

Task 3 implements the accepted architecture-review fixes without changing historical SQL.

## Changes

- The build job exposes its image digest. Supported deploys and rollbacks use the same `repository@sha256:…` reference for migrations, API, and worker. The controller rejects mutable tags, differing API/worker images, and images below the `sanvi-hardened-v1` compatibility floor. GitHub workflow concurrency and the host's existing `flock` serialize release operations.
- Migrations now run on the deployment host inside the same controller/lock as the traffic switch. The immutable image supplies both its SQL and its classification manifest. Ordinary rolling deployment rejects pending maintenance migrations and any unclassified migration before changing serving containers. Maintenance mode stops the proxy, both API slots, and the worker before schema changes; a persistent marker blocks accidental ordinary recovery after failure.
- Historical migrations are conservatively marked maintenance because their compatibility with an earlier running image has not been established. The three new additive remediation migrations are marked rolling. New migrations must enter `deployment/migration-policy.json`; the policy coverage regression fails closed when an entry is missing. Rollback never runs down migrations automatically. Applied database migration versions absent from the candidate image are rejected explicitly as an unsupported schema before migration or serving-process changes, including in maintenance mode.
- Compose loads a host-provisioned raw environment file into API/API-next/worker. The controller requires the file and enforces owner-only permissions on Linux. Migrator credentials use a separate owner-only file supplied only to migration containers. Dollar signs and quotes remain literal; secret files are never sourced or printed.
- The worker overrides the inherited API probe with `sanvi-cli healthcheck --port 9091 --path /readyz`. Port 9091 is exposed only on the private Compose network, with no host publication; a metrics collector on that network should scrape `worker:9091/metrics`.
- API readiness gates traffic switching. The nginx ingress overwrites `X-Forwarded-For` with its resolved peer address and clears `Forwarded`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Forwarded-Port`, and `X-Real-IP`. The API trusts only the ingress's static `/32`, derived from the same `SANVI_PROXY_IP` configuration as nginx's address. The dedicated default subnet is `172.30.16.0/24`, with nginx at `172.30.16.10`; override both `SANVI_BACKEND_SUBNET` and `SANVI_PROXY_IP` together if this conflicts with host networking.

## Host setup and assumptions

- Provision `/opt/sanvi/secrets/runtime.env` and `migrator.env` as 0400 or 0600, owned by the deployment user. Runtime values must include database connection/user/password, Redis URL, OTLP token and endpoint, and the enabled provider credentials required by existing configuration validation. Migrator values must include its separate database connection/user/password, `SANVI_ENV=production`, and TLS policy. These paths are host artifacts, never repository files.
- Require recent Docker Compose supporting raw `env_file` (2.30+), Bash, `flock`, Python 3, and host authentication to the private image registry. The image must contain the classification manifest; old images predating this fix fail closed rather than bypass migration checks.
- Because the nginx listener is published on host loopback, an outer host TLS proxy normally fronts it. That proxy must overwrite incoming client X-Forwarded-For with its TCP peer IP. Provision its exact container-visible source CIDR in `/opt/sanvi/secrets/trusted-edge-cidr` (non-secret) so nginx can resolve the real client before overwriting downstream forwarding headers. The generator rejects wildcard trust and directive injection. If this setting is absent, nginx trusts no upstream claims; users behind the outer proxy share that proxy's source identity. Do not use a broad network that contains untrusted clients.
- Initial rollout of the dedicated network may require recreating a previous Compose network during the maintenance window. Existing deployments must preserve secret files, the active-slot state, and recovery markers. A managed PostgreSQL backup/PITR policy and a verified prior-image/schema compatibility matrix remain operational release requirements.

## Compatibility floor and first hardened rollout

The supported image floor is the **first built image containing all of** `/app/deployment/image-contract` with value `sanvi-hardened-v1`, its migration-policy manifest and SQL, and the worker's management listener on port 9091. Record that first immutable digest in the deployment inventory when an image is actually built and verified; no existing deployed digest has been proven by this repository. The marker is a versioned release contract, not a claim that arbitrary earlier images support hardened deployment. The controller checks the image contract and policy before changing nginx configuration, migrations, or serving containers. It does not introduce a legacy health-probe bypass.

The first hardened rollout requires an explicit maintenance window and a verified pre-upgrade PostgreSQL snapshot/PITR restore point. Preserve the exact legacy image digests, controller and Compose revision, proxy configuration and slot state, and corresponding secret-manager configuration before applying changes. Rehearse restoration of that set. If a legacy Compose network exists, recreate it during that window as needed for the dedicated ingress address; then deploy the first hardened image with maintenance mode and verify API/worker readiness and core tenant workflows.

Routine rollback through this hardened controller supports only images at or above the floor whose migration files include **every currently applied database version**. It does not downgrade schemas or assert compatibility with an unknown older binary. If the first hardened rollout needs to be reversed to a pre-hardening application, use a separate incident maintenance procedure: stop the hardened writers, restore the verified pre-upgrade database snapshot/PITR state, restore the matching legacy controller/Compose/proxy configuration and image digests, and verify database/application compatibility before resuming traffic. Data written after the selected restore point requires an explicit reconciliation decision. Do not point a legacy image at an upgraded database, suppress its failed probe, or remove the compatibility marker check to force a rollback.

## PITR verification-helper repair

The combined 1,544-test run exposed a failure in `tests/recovery/tests/pitr.rs:59`: `start restored instance` reported `exit_code=None` with empty stderr after 31 seconds. The helper inspected Docker exec status for only four seconds **before** awaiting command-output completion, then retained that early status. `pg_ctl` legitimately allows 60 seconds for startup. The local testcontainers implementation documents that its output readers finish only when the command exits, so a startup beyond the early inspection window can leave a stale `None` even after the command actually completes.

The narrow repair moves stdout/stderr collection before exit-status inspection and preserves the existing short Docker-status consistency retry, command timeout, and every restore assertion. No tests were skipped and no assertion/timeout was relaxed. An unpatched focused diagnostic rerun passed in 13.868 seconds; its temporarily retained container log confirmed both pinned recovery and full archive replay completed and reached read-write readiness with the new migrations. This is a load-dependent helper race, not evidence of a Windows-specific PostgreSQL or migration defect.

After rebuilding the repaired test, `DOCKER_API_VERSION=1.47 bash scripts/test.sh --quiet -p recovery-tests --test pitr` passed 1/1 in 13.469 seconds, including both restore consistency scenarios. One intermediate attempt failed because the retained diagnostic container still held fixed port 45433; that exact test container was inspected and removed, then the clean rerun passed. The combined suite's other results belong to root verification; this focused pass does not assert that the full suite is green.
