# sanvi-backend — Numbered Requirements

Numbered requirements are the layer that task files trace to. They are introduced **from phase 09
onward**; phases 00–08 shipped before this practice and remain documented by their
`phase-NN-*/implementation-plan.md` files, which stay authoritative for what was built.

IDs are phase-prefixed (`FR-9xx` = phase 09, `FR-10xx` = phase 10, …) so they never collide and so a
requirement's phase is readable from the ID alone. IDs are permanent: when a requirement changes,
edit its text and note the change; when it is dropped, mark it `withdrawn` rather than reusing the
number.

`python3 ~/.claude/skills/sdlc-planner/scripts/sdlc.py check` verifies that every requirement here is
covered by at least one task in `tasks/`, and that every task names a requirement.

## Phase 09 — Tenant Payment Providers (0.10.0)

Derived from [`phase-09-tenant-payments/implementation-plan.md`](phase-09-tenant-payments/implementation-plan.md)
and sliced into tasks per [`tasks/phase-09/README.md`](tasks/phase-09/README.md).

### Functional

| ID | Requirement |
|---|---|
| **FR-901** | A tenant admin can connect their own Stripe account through Accounts v2 (`POST /v2/core/accounts`) plus an embedded onboarding Account Session, and the platform persists a connection row holding the resulting `acct_…`. Exactly one active connection per tenant per provider. |
| **FR-902** | `GET /api/v1/tenant/payments/providers` returns a provider catalog derived from the registered adapters (never a hardcoded handler list), gated on the `payments.stripe_connect` entitlement and the `payments.read` permission. |
| **FR-903** | `GET /api/v1/tenant/payments/connections/{id}` exposes status, capabilities, outstanding requirements with deadlines, blockers, and a server-computed `can_accept_payments` derived **only** from `configuration.merchant.capabilities.card_payments.status == "active"`. |
| **FR-904** | Connection lifecycle is driven by connected-account webhooks through an explicit state machine (`Pending → Onboarding → {Active, Restricted, Rejected} → Disconnected`), with a reconciliation job as the safety net for missed deliveries. |
| **FR-905** | `POST /api/v1/tenant/checkout` creates a Checkout Session **on the connected account** (direct charge) with dynamic payment methods, the tenant's locale, and success/cancel URLs validated against a verified tenant domain; `GET /api/v1/tenant/checkout/{id}` is the only source of order truth. |
| **FR-906** | Payment, refund, dispute and payout state is projected into tenant-scoped read models from webhooks (never fetched from the provider per request), queryable with the documented filter set, a per-payment timeline, and an audited server-side CSV export. |
| **FR-907** | A principal holding `payments.refund` can issue a full or partial refund on the connected account, idempotently, with a required reason, rejecting over-refunds with the remaining refundable amount. Refunds issued in the tenant's own Stripe Dashboard reconcile into the read model. |
| **FR-908** | When a tenant enables automatic tax, liability is routed to the connected account (`automatic_tax.liability = { type: 'account', account: acct_id }`), gated on a preflight that the account's tax settings are `active` and registrations exist, re-verified on a schedule. |
| **FR-909** | A per-tenant/per-plan application fee is configurable in the `platform-admin` context (never the tenant API), **disabled by default in 0.10.0**, applied as `payment_intent_data.application_fee_amount` on direct charges when enabled, and disclosed to the tenant it applies to. |
| **FR-910** | `DELETE /api/v1/tenant/payments/connections/{id}` disconnects a provider, refusing with `409` and structured blockers (`in_flight_payments`, `open_disputes`, `pending_payouts`) while money is unresolved. Historical records are retained; reconnecting creates a new connection row. |

### Non-functional

| ID | Requirement |
|---|---|
| **NFR-901** | **Sanvi is never the merchant of record.** Direct charges only; `defaults.responsibilities.fees_collector` and `losses_collector` both `"stripe"`; funds never touch the platform balance. Enforced by CI gates, asserted in the sandbox, and alarmed in production (any platform-balance movement from a tenant transaction pages). |
| **NFR-902** | No deprecated Connect v1 pattern exists anywhere in the repository — `type: 'standard'\|'express'\|'custom'`, `charges_enabled`, `payouts_enabled`, `payment_method_types`. `scripts/check-connect-invariants.sh` fails the build on any occurrence. |
| **NFR-903** | Every tenant-scoped `payments.*` table carries `tenant_id` and is protected by RLS; `payments.webhook_events` is platform-scoped and not tenant-readable. The schema stores **no** card data, bank details, or onboarding PII — only identifiers, status, and amounts. |
| **NFR-904** | Every mutating payments endpoint accepts and requires `Idempotency-Key`, enforced locally **and** passed through to the provider, so a retried request never produces a second side effect at Stripe. |
| **NFR-905** | The Connect webhook transport verifies the signature on the raw body before parsing, stores then processes, dedupes by event id, drops stale out-of-order events, dead-letters poison events with replay from `apps/cli`, and rejects events for unknown accounts without creating rows. The Connect signing secret and the phase-04 platform secret must not validate each other's events. |
| **NFR-906** | No `stripe::` type appears in a port signature or anywhere in the domain or application layers — enforced by `scripts/check-layering.sh`. Adding a second provider requires only a new adapter, proven by the fake provider adapter used in tests. |
| **NFR-907** | Money is represented as minor units plus an ISO-4217 code, never a float or `numeric`; arithmetic is currency-checked. JPY (zero-decimal) is correct at every layer and is a required test case. |
| **NFR-908** | Metrics, traces, alerts and runbooks exist for every payments failure mode before the phase is tagged; the checkout path is traced end to end including the outbound Stripe call. PCI scope stays SAQ-A. |
| **NFR-909** | Account Session client secrets are never persisted and never logged. The Connect restricted API key and Connect webhook signing secret are distinct per environment, distinct from the phase-04 platform credentials, and carry only Connect permissions. |

## Phase 10 — Advertising & Campaigns (0.11.0)

Derived from [`phase-10-advertising/implementation-plan.md`](phase-10-advertising/implementation-plan.md)
and sliced into tasks per [`tasks/phase-10/README.md`](tasks/phase-10/README.md).

### Functional

| ID | Requirement |
|---|---|
| **FR-1001** | `GET /api/v1/tenant/ads/platforms` returns a platform catalog assembled from the registered adapters (never a hardcoded list), carrying per platform its display metadata, entitlement key, connection state, and a versioned **capability matrix** — objectives, budget types, minimum budgets by currency, schedule granularity, targeting dimensions, creative placements and asset specs, and text limits **per locale**. The matrix is the single source both the backend validator and the frontend form engine consume. |
| **FR-1002** | A tenant admin connects a Google Ads and a Meta ad account through a backend-driven OAuth flow whose `state` is a signed, single-use, tenant-bound nonce, selects the account when several are eligible (a Google manager account resolves to many customer ids), and the platform persists one connection per `(tenant, platform, external_account_id)` holding the account's currency and timezone. |
| **FR-1003** | Connection health is maintained without tenant action: refresh tokens are renewed before expiry with jitter; a revoked or permanently failing credential sets `status = Disconnected`, emits `AdAccountDisconnected`, notifies the tenant once, and **pauses** dependent jobs rather than retrying; a granted-scope subset surfaces as a re-consent state naming the missing scope. `GET /connections` exposes `can_sync`, `can_upload_conversions`, `token_expires_at`, `scopes_missing`, `last_error`, `last_synced_at` as server-computed fields. |
| **FR-1004** | A tenant drafts a campaign tree (campaign → ad group → ad → creative) in Sanvi, validates it against the platform's capability matrix through `POST /campaigns/{id}/validate` returning **field-addressed** violations, and publishes it to the platform. `PATCH` on a published campaign requires `Idempotency-Key` and `If-Match` on the campaign revision; a stale revision returns `409` with the current state. |
| **FR-1005** | A nightly and on-demand reconciliation job pulls the remote campaign tree per connection and compares it field-wise against our last-known snapshot: a non-contradicting remote change updates the snapshot silently; a change that contradicts our intent sets `drift` with a diff, emits `CampaignDrifted`, and notifies. Reconciliation **never writes back**. `POST /campaigns/{id}/drift` carries an explicit `keep_theirs` or `reapply_ours` resolution, idempotent per drift revision. |
| **FR-1006** | The Google Ads adapter implements `AdPlatformPort` (auth, list accounts, campaign-tree CRUD, fetch metrics, upload conversions) against a pinned API version and passes the same port contract suite as the fake adapter, with per-ad review status and platform rejection reasons surfaced verbatim. |
| **FR-1007** | The Meta adapter implements the same `AdPlatformPort` against the Marketing API with its own capability matrix, and creatives are persisted with assets, per-locale copy, and placement assignments, validated against the target placements' asset specs **at upload time**, not at publish time. |
| **FR-1008** | `POST /api/v1/public/track`, mounted on the tenant's own verified domain, captures a conversion event with a stable server-issued `event_id`, click ids (`gclid`, `gbraid`, `wbraid`, `fbc`, `fbp`) distinguishing absent from empty, and a value taken from the phase-09 payment record where one exists (a client-reported value is recorded as such). Storage is idempotent on `(tenant_id, event_id)`. |
| **FR-1009** | Every captured event resolves the phase-05 `DirectiveResolver` for `ads_measurement` **and**, where the receiving vendor is registered as a third party rather than a service provider, `sale_or_share` / `targeted_advertising`, and persists the full `ConsentSnapshot` (purposes, answers, signal source, jurisdiction, resolver version). A denied purpose stores the event analytics-only with `suppressed_by_directive` naming the purpose and the source, and never queues it. |
| **FR-1010** | Permitted events upload to Google Ads (offline/enhanced conversions) and Meta (Conversions API) exactly once, batched, retried with backoff, deduplicated on the shared `event_id`, with **per-platform** upload state, permanent-versus-transient failure classification, a DLQ for parked events, an audited manual retry for retryable rows only, and a per-event diagnostics projection carrying capture, gate, and attempt history. |
| **FR-1011** | Audience/customer-list sync requires `sale_or_share` **and** `targeted_advertising` per subject; opted-out subjects are excluded from new lists and **removed from existing ones on the next scheduled refresh**. A withdrawal or opt-out after upload triggers a deletion/suppression request to each platform that supports one, recording an explicit unpropagated outcome where none exists. |
| **FR-1012** | Metrics ingestion runs per connection — hourly for the current day plus a rolling backfill of the trailing 30 days — as an upsert keyed by `(tenant, platform, campaign, date)`, maintains `metrics_daily` and its rollups, joins phase-09 revenue by `order_ref` (and by date bucket where attribution is impossible, reported at platform level rather than distributed by a guess), and serves `/metrics`, `/metrics/summary`, `/metrics/export`, `/metrics/freshness` from rollups over bounded date ranges, each row carrying its source currency, ad account timezone, and a `restating` marker. |
| **FR-1013** | Per-campaign and per-tenant daily and monthly budget caps are enforced by us in addition to the platform's own controls: a threshold evaluator runs after each ingestion cycle and emits `SpendThresholdReached` at 80 % and 100 % once per period per scope; auto-pause is off by default, pauses through the ordinary attributed mutation path, never auto-resumes, and a dry-run reports what would have been paused with no side effects. |
| **FR-1014** | The advertising context implements the phase-05 `PersonalDataProvider` — exporting and erasing hashed identifiers, click ids, and audience membership, retaining the consent snapshot under the registered statutory override — and Google and Meta are registered in the sub-processor registry with their **role** (service provider/contractor vs third party), contract terms, and APPI/EU transfer disclosures, which is the field FR-1009's gate reads. |

### Non-functional

| ID | Requirement |
|---|---|
| **NFR-1001** | **No identifier leaves Sanvi without a live directive that permits it.** Every `ConversionSinkPort` implementation takes a `ConsentSnapshot` as a required argument, so an upload path without one does not compile; the upload worker reads the decision recorded at capture and re-checks only for *withdrawal*, never upgrading a suppressed event after a later consent. An upload attempted without a stored snapshot pages. |
| **NFR-1002** | No raw PII exists in this context: identifiers are normalised then SHA-256 hashed (lowercase, trim, strip dots and plus-tags for email; E.164 for phone) and only hashes are persisted, logged, traced, or sent. A grep gate fails on any raw `email`/`phone` field name inside the context's adapters, and a full-capture assertion over the events table and tracing output finds neither. |
| **NFR-1003** | OAuth refresh tokens are encrypted with the phase-05 envelope scheme under a per-tenant DEK, access tokens are cached in memory only, and `SecretRef`'s `Debug`/`Display`/`Serialize` impls redact. Nothing token-shaped reaches a log line, trace attribute, error message, or response body; access to the decrypt path is audited from the first call. Connect and disconnect require fresh MFA and are audited with the actor, account, and scopes granted. |
| **NFR-1004** | Every `advertising.*` table carries `tenant_id` and is protected by RLS, **verified to inherit to child partitions by name**. `conversion_events` and `metrics_daily` are monthly range partitions with a partition-creation job scheduled from the first migration and retention windows registered in the phase-05 data map before either table holds a row. |
| **NFR-1005** | Money is minor units plus an ISO-4217 code, always paired with the currency of the ad account it came from; JPY is zero-decimal and correct at every layer. **No converted value is ever persisted** — FX is applied in the query layer for display only, from dated rate snapshots, and a rendered conversion carries its rate date. Cross-currency sums do not exist. |
| **NFR-1006** | Platform-reported conversion value and Sanvi-observed revenue are reported side by side, each labelled with its provenance, in the API and in every export. There is no blended attribution field anywhere — grep-asserted — and zero spend yields null, never infinity. |
| **NFR-1007** | Every mutating advertising endpoint accepts and requires `Idempotency-Key`; every mutation is recorded in an append-only change log with the actor, timestamp, field-level before/after, source (`sanvi` \| `platform`), and mutation id, so "who paused this campaign" is answerable and a publish interrupted by a timeout cannot create two campaigns. |
| **NFR-1008** | No platform-specific type or branch exists in the domain or application layers; platform difference is expressed only as capability-matrix data and adapter code. Adding a third network requires an adapter plus a matrix, proven by the fake adapter's asymmetric third matrix, and every adapter passes the same `AdPlatformPort` contract suite. |
| **NFR-1009** | Metrics ingestion is idempotent under restatement: re-ingesting a day **replaces** that day at the `metrics_daily` grain and at every rollup level. An append here silently doubles history, so it is asserted at every aggregation level rather than at the entry point. |
| **NFR-1010** | `/api/v1/public/track` is unauthenticated by design and hardened accordingly: per-tenant-domain signed rotatable site key, strict `Origin` checks, payload size caps, per-IP and per-domain rate limits, bot filtering, and no reflection of input or existence in any response. Platform API quota is budgeted per connection so one tenant's bulk edit cannot exhaust the shared developer-token quota. |
| **NFR-1011** | Metrics (`ads_sync_duration`, `ads_sync_failures_total`, `conversion_upload_total`, `conversion_suppressed_total{reason,source}`, `ads_token_refresh_failures`, `metrics_ingestion_lag_hours`, `budget_threshold_alerts_total`), their alerts (ingestion lag > 6 h, upload failure ratio > 5 %, token refresh failures, spend anomaly > 3σ, DLQ depth), end-to-end traces on the tracking path, and a runbook per failure mode all exist before the phase is tagged. |

## Phase 11 — Hardening, Observability & GA (1.0.0)

Derived from [`phase-11-hardening-ga/implementation-plan.md`](phase-11-hardening-ga/implementation-plan.md)
and sliced into tasks per [`tasks/phase-11/README.md`](tasks/phase-11/README.md).

Phase 11 adds no user-facing capability — the single exception is the quota and usage surfaces in
FR-1118, because a limit users cannot see is a support ticket with extra steps. Every other
requirement here is about *evidence*: a number, a report, or a rehearsed drill. Requirements that
would normally read "the system does X" therefore read "the system is **shown** to do X", and the
showing is the deliverable.

### Functional

| ID | Requirement |
|---|---|
| **FR-1101** | `apps/cli` gains `seed-scale`, a deterministic production-shaped data generator: the same seed produces identical row counts and checksums, the distribution is a long tail of small tenants plus a middle band plus three deliberately hot tenants (heavy `audit.entries`, heavy `advertising.metrics_daily`, high `payments` volume with many refunds), locale mix skewed to include Japanese content, themes published at several revisions, and custom domains at each lifecycle state. It refuses to run unless the target database name matches the staging pattern, and the guard cannot be bypassed by environment variable alone. |
| **FR-1102** | `GET /api/v1/system/build` returns commit sha, semver, built-at, and environment — unauthenticated, cacheable, carrying no tenant data — so a field measurement from RUM, the error tracker, or the status page can always be attributed to an exact build. |
| **FR-1103** | `tests/load/` carries k6 scenarios for the five load shapes (storefront read, admin write, checkout create, webhook flood, conversion upload), driven by `just perf`; every run writes a JSON artifact to `benchmarks/<scenario>/<rc-tag>.json`, and `just perf-compare` diffs two runs and exits non-zero past a per-metric threshold. A `benchmarks/baseline-<date>.md` snapshot records `pg_stat_statements` top 50, index usage, table and index sizes, cache hit ratios, and pool saturation over four weeks of staging/beta. |
| **FR-1104** | `docs/release/ga-checklist.md` is assembled from the acceptance criteria of every phase 00–11, each line carrying an owner column, and a CI job fails while any line has no owner. `docs/runbooks/staging-parity.md` records instance sizes, multi-AZ posture, connection limits, and CDN configuration with the deltas from intended production called out explicitly. |
| **FR-1105** | Every application use case across the thirteen contexts emits a span named `context.usecase` carrying tenant id, actor, and outcome, and every outbound call (Postgres, Redis, Kratos, Keto, Stripe, ACME/DNS, Google/Meta Ads, object storage) is a child span with peer attributes. The coverage matrix is a committed artifact and a CI test walks the registered use cases and fails on an unspanned one. Server-rendered documents and API responses carry the W3C `traceparent`, and every problem-details error carries `trace_id`. |
| **FR-1106** | Each of the six service journeys has an SLI with its exact query, a target confirmed against the FR-1103 baseline (renegotiated *now* and the reason recorded where the baseline says a proposed target is unreachable), a dashboard defined in code, a multi-window multi-burn-rate alert split into paging and ticketing tiers, and a named owner. The error budget policy — burning > 50 % of a monthly budget freezes feature merges for that context — is published and linked from the contributing guide. |
| **FR-1107** | One dashboard exists per bounded context (RED plus that context's domain metrics) and one per user journey, all defined in code and reviewed like code. `docs/runbooks/` holds one runbook per alert with detection, triage, mitigation, and escalation. |
| **FR-1108** | The top 20 endpoints by (requests × latency) from the baseline are profiled with `cargo flamegraph` and `tokio-console`, with a before number recorded per endpoint; missing and duplicate indexes are resolved, RLS predicate cost is measured per table, `EXPLAIN (ANALYZE, BUFFERS)` assertions land in the perf suite, N+1s are eliminated across every context's read models with statement-count tests guarding each, connection pools are sized from measured concurrency per app with statement timeouts and saturation alerting, and caches are audited for hit ratio, single-flight stampede protection, negative caching, justified TTLs, and tenant-scoped keys. |
| **FR-1109** | Every collection endpoint in the thirteen specs uses cursor pagination with a bounded page size; no unbounded list remains. A request that cannot complete inside its statement-timeout budget returns a problem-details error rather than holding a connection. |
| **FR-1110** | `docs/runbooks/capacity.md` publishes a written capacity model mapping requests/tenant/day to CPU, memory, DB IOPS, and Redis memory using the constants measured in this phase, with a documented scaling trigger per resource, and is referenced by the on-call material. |
| **FR-1111** | Anonymous storefront SSR responses are cached behind `platform.ssr_cache`, keyed by `(tenant, locale, theme revision, device class)`, with single-flight on miss, explicit `Vary`, a documented invalidation path on theme publish and content change, and a hit-ratio metric on the storefront dashboard. Authenticated responses are never cached, asserted by a test rather than by a code comment. Static assets are immutable and hashed; HTML lifetimes are set per app; Brotli and LCP-resource preload/early hints are configured for the storefront's top templates. |
| **FR-1112** | `docs/runbooks/dependency-matrix.md` records, for Postgres, Redis, Kratos, Keto, Stripe, DNS/ACME, Google Ads, Meta, and object storage, the behaviour when slow, when erroring, and when down, plus timeout, retry policy, circuit-breaker thresholds, and the user-visible consequence — one row per dependency per failure mode, each row implemented **and** covered by a test that injects that failure mode. |
| **FR-1113** | The degradation rules are implemented: Redis down serves from Postgres at reduced throughput and sheds non-essential work; Keto down denies writes by default and allows cached reads for ≤ 30 s then denies; Stripe down queues and retries under idempotency keys and never double-charges; ad platforms down queue conversions with their directive snapshot and never drop them; object storage down serves placeholders and blocks uploads with an honest error. Responses served from a degraded path carry a documented header. |
| **FR-1114** | Load shedding above a measured concurrency ceiling returns `503` with `Retry-After` and the `platform/overloaded` problem type behind `platform.load_shedding`, queues throughout `crates/platform/messaging` are bounded, workers handle poison messages with dead-letter queues and an operator path back plus retry budgets, and **per-tenant fairness** prevents one tenant's burst from consuming the shared pool — tested with a hot tenant from the FR-1101 seed. |
| **FR-1115** | A rolling restart under k6 load drops zero requests, and migrations follow an expand/contract two-phase pattern enforced in CI: a migration touching a live column without a matching contract step fails unless explicitly annotated. Five chaos drills (kill the primary DB, sever Redis, expire all sessions, replay a webhook flood, blackhole one ad platform) each run as a scheduled game day with a hypothesis, a runner who did not write the code, a dashboard to read, and a findings list with owners. |
| **FR-1116** | The route/permission matrix is a **generated** artifact derived from the OpenAPI documents plus handler metadata — every route with its required permission, tenant scoping, and rate-limit class — reviewed by two people and checked in, with a router-walk test failing any route that appears without one. `docs/security/threat-model.md` is refreshed with STRIDE per trust boundary across all thirteen contexts, explicitly covering the surfaces phases 08–10 added: tenant custom domains and subdomain takeover, the public tracking endpoint, ad-platform OAuth tokens, Connect keys and webhooks, and the phase-03 impersonation path. |
| **FR-1117** | Per-tenant and per-IP abuse quotas are enforced on every surface that costs money or reputation — signup, invitation, password reset, the public tracking endpoint, domain purchase, and outbound notification sends — with bot filtering on tracking, fraud checks on domain purchase, and velocity limits on invitations, none of which degrade legitimate traffic at 3× peak. |
| **FR-1118** | `GET /api/v1/system/health` reports liveness without touching the database, and `GET /api/v1/system/ready` reports dependency readiness as *states* — never hostnames, versions, or error strings — both unauthenticated and consumed by the status page and external monitors. Real probes from outside the perimeter exercise the six SLO journeys behind `platform.status_probes`. |
| **FR-1119** | Backups run as continuous WAL archiving plus daily base backups with retention aligned to the phase-05 rules, encrypted at rest, with backup-store access audited separately from the database. A full restore, a point-in-time restore verified across outbox/audit chain/payment records, and a single-tenant restore into the live system with a dry-run mode are each rehearsed and documented, and a monthly restore rehearsal is scheduled with an owner beyond GA. |
| **FR-1120** | Every credential is rotated end to end in a drill with a measured duration and a runbook per credential: database, Redis, Kratos/Keto, Stripe platform and restricted keys, Connect webhook secrets, ad OAuth client secrets, the tracking site-key signing secret, the phase-05 KEK/DEK hierarchy, and the session signing keys. Old credentials are asserted to be rejected after rotation, not only new ones asserted to work. |
| **FR-1121** | On-call is live before GA: a defined rotation, a written escalation policy with response-time expectations per tier, alert routing tested end to end with a synthetic page, a shadow week whose primary did not write the alerts, and a written degraded-mode operating procedure rehearsed in the same window as the restore drill. |
| **FR-1122** | All thirteen OpenAPI documents pass one consistency pass — resource naming, pluralisation, casing, pagination, filtering and sorting grammar, timestamp and money representation, enum naming, and a single namespaced problem-type registry — enforced by a spectral-style linter in CI against a written style guide, after which `/api/v1` is frozen and a CI job fails any breaking change without an explicit reviewed exception label. |
| **FR-1123** | The deprecation policy is published before anything is deprecated — six months' notice, `Deprecation` and `Sunset` headers, a changelog entry and a migration note per deprecation — with header emission, changelog generation, and a registry of deprecated elements and sunset dates enforced by the build. Public API documentation is generated from the spec with worked examples per journey and per locale, JPY and zero-decimal handling included in the examples rather than in a footnote. |
| **FR-1124** | Per-plan rate limits enforced at the HTTP boundary, keyed by tenant and by API credential with a stricter bucket for unauthenticated and public endpoints, return `429` with `Retry-After`, `RateLimit-Limit`, `RateLimit-Remaining`, and `RateLimit-Reset` and documented burst behaviour. Limits are derived from the FR-1110 capacity model and the derivation is written next to the numbers. |
| **FR-1125** | Metered quota dimensions per plan (API requests, tracked conversions, storage, custom domains, seats, notification sends) are counted in a way that survives a restart and a Redis flush, exposed through `GET /api/v1/tenant/usage` as current-period usage and limit, and enforced with an entitlement-aware error naming the upgrade path rather than saying "forbidden". The usage endpoint's numbers are the same numbers enforcement uses. |
| **FR-1126** | A backwards-compatibility replay suite of real staging client requests (scrubbed) runs against every release candidate, asserting status, shape, and header compatibility, and blocks the release on incompatibility. |
| **FR-1127** | Every validation error emitted by the thirteen contexts is field-addressable so a client can associate the message programmatically and build a linked error summary; every collection endpoint has a specified deterministic ordering tie-broken by id; and phase-06 notification and email templates meet the same contrast and structure rules as the apps. |
| **FR-1128** | `audit.entries`, `platform.outbox`, and the webhook event tables carry the same monthly range partitioning phase 10 established for the advertising tables, with one partition-creation job covering **all** partitioned parents from a single registry and an alert when next month's partition does not exist by the 25th. |
| **FR-1129** | Archival policies exist per table — what moves, at what age, to which cold object storage encrypted under the phase-05 envelope scheme, and how it is read back — behind `platform.archival`, with the first run measured on staging scale data for duration and IO impact, and a rehearsed restore path (runbook plus CLI command) that returns an archived range to a queryable table with identical rows, ordering, and checksums. A read that needs archived rows either restores them or says the range is archived; a silently-partial result is a defect. |
| **FR-1130** | The phase-05 retention rules are proven to *run*: a per-class report generated from live data (rule, last run, rows affected, oldest surviving row) with an alert when a class has not run inside its window. Bloat is measured per table at scale, autovacuum is tuned per table size, and unused and duplicate indexes are removed with before/after sizes recorded. |
| **FR-1131** | `POST` and `GET /api/v1/platform/tenants/{id}/offboarding` (`platform.tenant.offboard`) run an idempotent export-then-purge: the export reuses the phase-05 export machinery and is verified before the purge starts; the purge covers every context including partitions, archives, caches, search indexes, and object storage; and the purge report enumerates what was removed per context and what was lawfully retained with the reason and retention end date. An automated residual scan after the purge fails the job loudly on any surviving row. |
| **FR-1132** | An evidence pack generates per jurisdiction (EU/UK, Japan, each US state in scope) from live configuration with the generating build sha and timestamp embedded: Art. 30-style records from the phase-05 data map, risk assessments for the high-risk processing added in phases 09 and 10, the sub-processor list with each party's role, purpose, location, and transfer mechanism, retention rules as published *and* as executed from FR-1130's report so the two columns can be compared, and the period's DSR and appeal metrics. |
| **FR-1133** | A live-fire DSR drill runs per jurisdiction — access, erasure, US opt-out including a GPC signal arriving on a storefront under a tenant custom domain, and an appeal — end to end on scale data, timed against that jurisdiction's statutory clock rather than an internal SLA, with the runner and result recorded. A test enumerates registered `PersonalDataProvider`s and fails when one is missing from either the access or the erasure path. |
| **FR-1134** | Erasure propagation is verified to reach archives, backup policy notes, caches, search indexes, ad-platform suppression lists, and the payment provider's retained records, with each destination either purged or documented as lawfully retained with an end date. A breach tabletop exercises the per-jurisdiction obligation calculator on a deliberately awkward scenario — a multi-state US incident with one EU data subject and encrypted data at rest — producing a timeline with decisions and their bases. |
| **FR-1135** | The notice and notice-at-collection diff against what counsel last approved is produced **by the generator**, not by someone reading two documents side by side, and counsel reviews the diff against what the system actually does. |
| **FR-1136** | Every phase 00–11 acceptance criterion is re-executed as an automated or documented gate with its `ga-checklist.md` owner signing the line, the full benchmark harness re-runs on the release candidate with `perf-compare` against `rc.1` and each intervening slice, dead feature flags are removed one commit at a time, phase 11 flags are set to their GA defaults, and the release's migrations are applied and reverted on a staging clone carrying scale data by someone who did not write the release. |
| **FR-1137** | `v1.0.0` ships through a staged rollout — canary then a percentage ramp with an automatic halt on SLO burn or error rate, each stage's dwell time defined in advance — tagged with the changelog, public API docs, SBOM, and provenance attestation, with the deprecation registry empty. Everything time-boxed out of phase 11 is recorded in a post-GA backlog with owners and dates, and the first quarterly SLO review is on a calendar. |

### Non-functional

| ID | Requirement |
|---|---|
| **NFR-1101** | **Nothing is claimed that has not been measured, and nothing is trusted that has not been rehearsed.** Every optimisation slice opens by recording the current number and closes by recording the new one, in the same harness, against the same production-shaped data; a regression against the stored baseline blocks the merge, not the release. Every slice commits an evidence artifact — a report, a benchmark JSON, a drill log, or an audit result with a date and a named runner. A slice with no artifact did not happen. |
| **NFR-1102** | Phase 11 adds no user-facing capability. The only exception is FR-1125's quota and usage surfaces. A change that alters a response body outside FR-1122's consistency pass belongs in another phase. |
| **NFR-1103** | A CI scanner runs the log emitter over a fixture corpus containing every PII-shaped value the platform holds — emails, phone numbers, addresses, tokens, card metadata, hashed identifiers, base64-wrapped tokens — and **fails the build** on any leak. Field names are standardised across contexts and levels are tuned for production volume with a documented cost estimate per level. |
| **NFR-1104** | Load at 3× projected peak holds every FR-1106 latency SLO with < 70 % utilisation on every resource; a 10× spike for two minutes degrades within the error budget and recovers without a restart; and a 24-hour soak shows flat memory, no connection growth, and no unbounded task accumulation. |
| **NFR-1105** | No unbounded outbound call exists: every dependency call carries a timeout and a circuit breaker, enforced by a CI gate that fails on an HTTP client constructed without a timeout. Circuit breakers and timeouts are not flag-gated — an unbounded call is never the safer default. |
| **NFR-1106** | `429` and `503` are distinct and never conflated: `429` means the caller asked too often, `503 platform/overloaded` means the platform is too busy. Client backoff strategy differs, so the codes must. Load shedding never sheds a webhook or a payment callback. |
| **NFR-1107** | RPO ≤ 5 min and RTO ≤ 1 h are **validated**, not asserted: a timed drill records date, build, runner, start time, end time, and data-loss window, and a single-tenant restore leaves every neighbour tenant's rows byte-identical. |
| **NFR-1108** | All five CI scanners — SAST, dependency audit (`cargo audit` / `cargo deny`), container scan, IaC scan, secret scan — block the build; none are advisory. An SBOM is published per release, dependencies are pinned, release artifacts carry provenance attestation, a written review policy governs new dependencies, and `cargo vet`-style auditing covers the security-critical path (crypto, HTTP parsing, SQL, template rendering). Accepted findings carry an expiry. |
| **NFR-1109** | Cross-tenant isolation is verified three independent ways: the phase-01 RLS matrix re-run against the full schema including every table added in phases 08–10 and every child partition **by name**, a manual IDOR sweep of every ID-bearing path, query, header, and body field using a valid session for the wrong tenant, and the external penetration test. A wrong-tenant request returns 404 or 403 and never leaks existence through timing or message differences. Every finding becomes a regression test that fails against the vulnerable commit. |
| **NFR-1110** | No high or critical penetration-test finding is open at GA; findings are triaged within 48 hours of receipt and the remainder are scheduled with an owner and a date. Security fixes roll forward, never back; the two changes that can break legitimate traffic — abuse quotas and CSP tightening — ship in shadow or report-only mode for one full staging traffic cycle with the observed false-positive rate recorded in the PR before enforcement. |
| **NFR-1111** | Every alert has a runbook and every runbook has an alert, enforced by a bidirectional CI cross-reference check. Alerts are symptom-based only: no alert on CPU, queue depth, or any other cause that does not by itself mean a user is having a bad time. New alert rules ship in the ticket tier first and are promoted to paging after a week of observed signal-to-noise. |
| **NFR-1112** | Evidence is generated from live configuration rather than written once: an evidence pack that cannot name the build that produced it is not evidence, generation is deterministic for a given configuration and period, and a configuration change is reflected in the next pack without code changes. |
| **NFR-1113** | Secret handling is inventoried and asserted: every secret's storage, rotation path, and blast radius is recorded, and envelope-encrypted material (phase-05 DEKs, ad tokens, Connect keys) is verified unlogged and unserialised with the phase 09/10 redaction tests extended to every type — debug, display, serde, and tracing capture. |
| **NFR-1114** | Security headers are specified rather than incidental — HSTS, frame-ancestors, referrer policy, permissions policy, and the CSP — asserted per app in a snapshot test. |
